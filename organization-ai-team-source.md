
# Базовая организация разработки командой ИИ-агентов
## Общая схема

Минимальный рабочий процесс:

```
Человек / CTO
    ↓ цель и приоритет
Агент-аналитик
    ↓ спецификация и критерии приёмки
Агент-разработчик
    ↓ код, тесты, PR
Агенты-ревьюеры
    ↓ замечания
Агент-разработчик
    ↓ исправления
CI и интеграционные тесты
    ↓
Human approval
    ↓
Merge и deploy
    ↓
Мониторинг → новые задачи
```

Начинать лучше не с виртуальной компании из десяти агентов, а с четырёх функций:
1. планирование;
2. разработка;
3. независимая проверка;
4. интеграция и эксплуатация.

Один и тот же тип модели может выполнять разные роли. Независимость достигается отдельными контекстами, полномочиями и критериями результата.

---

## Базовый стек

|Компонент|Назначение|
|---|---|
|GitHub Issues, Linear или Jira|Очередь задач и статусы|
|GitHub или GitLab|Репозиторий и pull request|
|Coding agent|Реализация задач|
|Git worktree или контейнер|Изолированная среда задачи|
|CI/CD|Сборка, тесты, проверки, deploy|
|Оркестратор|Запуск агентов и переходы между этапами|
|Логи, метрики, traces|Обратная связь после запуска|

Трекер задач выступает основной панелью управления:

```
Backlog
→ Specification
→ Ready
→ Development
→ Agent Review
→ Integration
→ Human Review
→ Deploy
→ Done
```

## Где хранятся инструкции

Минимальная структура репозитория:

```
AGENTS.md
ARCHITECTURE.md
WORKFLOW.md

agents/
  planner.md
  developer.md
  code-reviewer.md
  architecture-reviewer.md
  test-engineer.md
  incident-investigator.md

docs/
  specifications/
  architecture/
  adr/

tests/
scripts/
.github/workflows/
```

Назначение файлов:
- `AGENTS.md` — общие правила работы с репозиторием;
- `ARCHITECTURE.md` — архитектурные принципы и границы;
- `agents/*.md` — роли отдельных агентов;
- `WORKFLOW.md` — порядок прохождения задачи;
- `docs/specifications/` — спецификации конкретных задач;
- `scripts/` — единые команды проверки;
- CI — обязательные машинные проверки.

## Как описывается роль агента

Роль должна определять:
- назначение агента;
- какие данные он получает;
- какие документы являются источниками истины;
- какие инструменты ему доступны;
- что он может изменять;
- что ему запрещено;
- какие проверки он обязан выполнить;
- в каком формате вернуть результат;
- что означает `PASS`, `FAIL` или `BLOCKED`.

Например, архитектурный ревьюер:
- читает спецификацию, архитектуру и diff;
- запускает архитектурные и контрактные проверки;
- не изменяет код;
- возвращает список блокирующих нарушений и подтверждающие факты.

Роль — это постоянная должностная инструкция. Конкретная задача передаётся отдельно.

---

## Минимальные роли

### Planning Agent

Объединяет функции бизнес-аналитика, PM и системного аналитика.

Результат:
- цель;
- scope;
- acceptance criteria;
- ограничения;
- граничные случаи;
- предполагаемые тесты;
- декомпозиция работы.

Он не должен самостоятельно принимать принципиальные продуктовые решения, которых нет во входной постановке.

### Developer Agent

Получает утверждённую спецификацию и отдельную рабочую среду.

Он:
- изучает релевантную часть системы;
- воспроизводит текущее поведение;
- реализует изменение;
- добавляет тесты;
- запускает общую проверку;
- формирует PR и отчёт о выполнении.

Разработчику запрещается самостоятельно ослаблять тесты, менять acceptance criteria или выполнять несвязанный рефакторинг.

### Correctness Reviewer

Проверяет:
- выполнение требований;
- логические ошибки;
- граничные случаи;
- обработку ошибок;
- достаточность тестов;
- изменения вне scope.

### Architecture Reviewer

Проверяет:
- границы модулей;
- направление зависимостей;
- API и внутренние контракты;
- обратную совместимость;
- соблюдение архитектурных решений;
- отсутствие нежелательных связей между слоями.

Да, один агент может ревьювить другого. Reviewer должен запускаться в новом контексте и не иметь права изменять проверяемый код.

### Test and Integration Agent

Проверяет систему целиком:
- запускает интеграционные и E2E-тесты;
- анализирует CI;
- разворачивает staging;
- исследует логи и traces;
- создаёт отчёт о дефектах;
- возвращает задачу разработчику или передаёт человеку.

### Incident Investigator

Получает ошибку, логи и телеметрию.

Он должен:
- определить последовательность событий;
- локализовать вероятный источник;
- воспроизвести проблему;
- сформировать issue;
- при достаточной уверенности передать задачу разработчику.

## Автоматический workflow

Оркестратор последовательно выполняет следующие этапы:
1. Новая задача поступает из трекера.
2. Planning Agent создаёт спецификацию.
3. Другой агент проверяет спецификацию на полноту и тестируемость.
4. Для задачи создаётся отдельный worktree или контейнер.
5. Developer Agent реализует изменение.
6. Несколько reviewer-агентов независимо проверяют результат.
7. При наличии замечаний разработчик получает их и исправляет код.
8. Цикл `review → fix → review` повторяется до прохождения проверок или исчерпания лимита.
9. CI запускает детерминированные проверки.
10. Изменение разворачивается на staging.
11. Выполняются интеграционные и E2E-тесты.
12. Результат передаётся человеку для утверждения.
13. После deploy мониторинг создаёт новые задачи при обнаружении ошибок.

Ревьюеры могут запускаться параллельно:

```
Developer
    ↓
Correctness Reviewer
Architecture Reviewer
Security Reviewer
Test Reviewer
    ↓
Объединённый список замечаний
```

---

## Что делает оркестратор

Оркестратор не пишет код. Он управляет жизненным циклом работы:
- читает задачи из трекера;
- выбирает требуемую роль;
- создаёт изолированную рабочую область;
- передаёт агенту спецификацию и доступные инструменты;
- сохраняет состояние сессии;
- запускает следующие этапы;
- следит за лимитами и тайм-аутами;
- повторяет упавшие запуски;
- собирает результаты ревью;
- изменяет статус задачи;
- передаёт спорные случаи человеку.

Проще говоря:

```
Трекер определяет, что делать.
Роль определяет, как действовать.
Оркестратор определяет, кого и когда запускать.
CI определяет, прошёл ли результат объективные проверки.
```

## Что такое harness

Harness — вся среда вокруг модели:

```
репозиторий
+ инструкции
+ инструменты
+ sandbox
+ worktree
+ workflow
+ тесты
+ CI
+ логи
+ права
+ retry
+ human approval
```

Хороший harness должен обеспечивать:
- воспроизводимую среду;
- ограниченные полномочия;
- короткий цикл обратной связи;
- машинно проверяемый результат;
- сохранение состояния;
- наблюдаемость;
- безопасное восстановление после ошибки.

Главное — не промпты персонажей, а исполняемые ограничения.

---

## Архитектурные контракты

Архитектурный агент полезен, но критические правила следует закреплять кодом:
- запрещённые зависимости;
- границы модулей;
- циклические импорты;
- схемы API;
- совместимость контрактов;
- правила доступа к данным;
- структура миграций;
- ограничения безопасности.

Например:

```
domain не зависит от infrastructure
UI не обращается непосредственно к БД
межмодульные вызовы проходят через публичные интерфейсы
внешние данные валидируются на границе системы
```

Architecture Reviewer интерпретирует сложные нарушения, но базовые инварианты должны проверяться CI.

---

## Тесты как функция цели

Для каждой задачи необходимо определить:
- какое поведение существует до изменения;
- какое поведение ожидается;
- какой командой это проверить;
- какие доказательства должен предоставить агент.

Минимальный Definition of Done:
- acceptance criteria выполнены;
- добавлены необходимые тесты;
- unit-тесты проходят;
- контрактные тесты проходят;
- интеграционные тесты проходят;
- архитектурные проверки проходят;
- в staging нет новых ошибок;
- reviewer-агенты не нашли блокирующих дефектов;
- PR содержит проверяемые результаты.

ИИ не должен самостоятельно решать, что результат «достаточно хороший». Это определяется тестами, контрактами и политиками workflow.

## Границы ответственности

### В роли агента задаются

- специализация;
- допустимые действия;
- запрещённые действия;
- обязательные проверки;
- формат результата;
- критерии завершения.

### В workflow задаются

- порядок запуска агентов;
- параллельность;
- повторные попытки;
- лимиты циклов;
- переходы между состояниями;
- точки human approval.

### В спецификации задачи задаются

- цель;
- scope;
- требования;
- ограничения;
- acceptance criteria;
- ожидаемые тесты.

### В CI задаются

- объективные условия допуска;
- тесты;
- линтеры;
- архитектурные проверки;
- security checks;
- сборка и deploy.

Человек сохраняет контроль над:
- приоритетами;
- продуктовыми компромиссами;
- архитектурными принципами;
- изменениями безопасности;
- необратимыми миграциями;
- production-деплоем.

# Готовые harness и фреймворки

## OpenAI Symphony

Наиболее близкий пример к описанной модели.

Symphony превращает issue tracker в control plane: каждой активной задаче соответствует отдельная рабочая область и агентная сессия. Политика выполнения хранится в репозитории в `WORKFLOW.md`; оркестратор отвечает за запуск, retries, ограничение параллельности и восстановление после сбоев. Это открытая спецификация и reference implementation, а не готовый коммерческий продукт, который OpenAI планирует развивать как самостоятельную платформу.

Подходит как основа собственного минимального harness:

```
Linear или другой tracker
+ Symphony
+ Codex
+ GitHub
+ CI
```

## OpenHands

Наиболее готовая открытая основа именно для программирующих агентов.

OpenHands предоставляет Software Agent SDK, инструменты работы с shell и файлами, управление контекстом, подтверждение опасных операций и запуск локально или через отдельный сервер. Поддерживаются специализированные агенты, описанные Markdown-файлами с YAML-заголовком: имя, назначение, инструменты и системная инструкция. В документации также приведён двухэтапный пример `planning agent → execution agent`. 

Подходит для:
- исполнителей;
- reviewer-агентов;
- sandbox;
- собственных инструментов;
- построения специализированного software-development harness.

## CrewAI

CrewAI ориентирован на ролевые команды. Агенты определяются через роль, цель, инструменты и ограничения; конфигурацию можно хранить в YAML. `Crews` отвечают за автономное взаимодействие агентов, а `Flows` — за предсказуемый порядок, состояния, ветвления и циклы.

Подходит, когда требуется быстро описать:

```
аналитик
→ разработчик
→ ревьюер
→ тестировщик
```

Но git worktrees, CI, PR, sandbox и работу с логами потребуется интегрировать отдельно.

## LangGraph

LangGraph подходит для построения собственного строго управляемого оркестратора. Workflow представляется графом состояний с последовательными шагами, параллельными ветками, циклами и условиями выхода. Поддерживаются сохранение состояния, возобновление работы, отладка и human-in-the-loop. 

Подходит, когда процесс должен быть формальным:

```
specification
→ implementation
→ parallel review
→ fix loop
→ integration
→ approval
```

Недостаток — это общий agent framework, а не готовая система разработки ПО.

## AutoGen AgentChat

AutoGen предоставляет готовые типы команд:
- последовательный круг агентов;
- выбор следующего агента моделью;
- handoff между ролями;
- swarm;
- граф выполнения.

Команды можно приостанавливать, возобновлять и ограничивать условиями завершения. Документация отдельно предупреждает, что многоагентные команды требуют существенно больше scaffolding, чем один агент.

Подходит для экспериментов с взаимодействием ролей. Для полноценного software-development loop потребуется дополнительный harness.

## Mini-SWE-agent

Это компактный специализированный агент для решения задач в существующих репозиториях. Он получает problem statement, работает с кодом и инструментами и пытается исправить issue. Авторы SWE-agent сейчас рекомендуют mini-SWE-agent как более простой преемник исходного проекта.

Подходит как исполнитель внутри более крупного workflow, но не как оркестратор команды.

# Практический выбор

## Самый простой путь

```
GitHub Issues
+ один coding agent
+ отдельный worktree на задачу
+ два reviewer-агента
+ GitHub Actions
+ ручное управление статусами
```

Оркестратор сначала не требуется.

## Следующий уровень

```
Linear или GitHub Issues
+ Symphony-подобный оркестратор
+ Codex/OpenHands как исполнители
+ GitHub Actions
+ staging и observability
```

## Для самостоятельной разработки платформы

```
LangGraph или CrewAI Flows
+ OpenHands SDK
+ tracker API
+ worktree manager
+ CI/CD
+ собственная permission policy
```

Наиболее рациональная архитектура:

```
Symphony-подобная модель управления задачами
+
OpenHands или coding agent как исполнитель
+
обычный GitHub CI как источник истины
```

Не следует начинать с AutoGen/CrewAI-команды, свободно обсуждающей задачу между собой. Для разработки надёжнее фиксированный конвейер с отдельными исполнителями, независимым ревью и детерминированными тестами.
