# Протокол «агент ↔ агент» в Claude Code — выжимка

Разбор снимка исходников Claude Code версии **2.1.87**, ставшего публичным 31.03.2026 через
`.map`-файл в npm-пакете. Источник: репозиторий-зеркало `freecodexyz/free-code` (8,8 тыс. звёзд,
клон 54 МБ, 1 356 файлов TypeScript).

Ниже — **пересказ своими словами**, а не копия кода. Код принадлежит Anthropic, лицензии у снимка
нет; этот файл фиксирует знание о контрактах и не содержит исходников. Версия старая: на момент
разбора у нас стоит 2.1.177, то есть снимок отстаёт примерно на девяносто патч-версий, и часть
деталей могла измениться. Всё, что отмечено «за флагом», включается фича-флагом и в публичной
сборке может отсутствовать.

## Три уровня взаимодействия

1. **Субагент** — одноразовый помощник внутри одного хода: получает задачу, возвращает результат,
   переписки с ним нет. Параметры команды/имени в этом режиме недоступны.
2. **Тиммейт** — участник команды: у него есть имя, свой почтовый ящик, он живёт между ходами, его
   можно разбудить сообщением. Спавнится тем же инструментом агента, но с параметрами команды и
   имени.
3. **Внешняя сессия** (за флагом) — другая локальная сессия на этой же машине через сокет или
   удалённая сессия через мост; адреса вида `uds:/путь/к.sock` и `bridge:session_…`, обнаружение
   через отдельный инструмент списка пиров.

Правило вложенности: **тиммейт не может спавнить тиммейта**. Из контекста тиммейта эти параметры
убраны намеренно — иначе дерево агентов растёт без контроля.

## Команда — это список задач

Команда и список задач связаны один к одному: создание команды создаёт и её доску. На диске:

- `~/.claude/teams/<команда>/config.json` — участники: имя, внутренний id, тип агента;
- `~/.claude/teams/<команда>/inboxes/<агент>.json` — почтовый ящик каждого;
- `~/.claude/tasks/<команда>/` — доска задач команды.

Обращение — **только по имени**. Внутренний id участника существует, но в протоколе прямо
запрещено использовать его для адресации: имена читаемы человеком и переживают перезапуск.

## Почтовый ящик

Один JSON-файл на агента, массив сообщений. Запись — дописывание под файловой блокировкой
(перед записью файл перечитывается, чтобы не потерять чужие сообщения). У каждого сообщения есть
флаг «прочитано»; отметка ставится по индексу или пачкой, есть очистка ящика.

Ключевая деталь: **входящие не проверяют**. Агента не просят «заглянуть в ящик» — сообщения
доставляются в его контекст сами, отдельными репликами. Ящик — это транспорт, а не раздел, куда
надо ходить.

Входящее приходит обёрнутым в тег с идентификатором отправителя, цветом и кратким резюме, чтобы
UI и модель отличали чужое сообщение от собственного текста.

## Инструмент отправки

Поля:

| Поле | Что это |
|---|---|
| `to` | имя тиммейта, `*` — всем, `uds:…` / `bridge:…` — внешняя сессия (за флагом) |
| `summary` | 5–10 слов: превью в интерфейсе, чтобы человек видел суть без раскрытия |
| `message` | строка либо структурированный объект протокола |

Отдельная оговорка в промпте: широковещание `*` линейно по размеру команды и потому дорого —
его разрешают себе, только когда всем действительно нужно одно и то же.

И главное, что часто ломают: **собственный текстовый ответ агента другим агентам не виден**.
Пока не вызван инструмент отправки, сообщения не существует. Это же правило повторено в
надстройке к системному промпту тиммейта.

## Структурированные сообщения

Помимо текста есть типизированные сообщения; у всех пар «запрос → ответ» общий `request_id`,
по которому ответ сопоставляется с запросом:

| Тип | Смысл |
|---|---|
| `plan_approval_request` / `plan_approval_response` | тиммейт показывает план, лид одобряет или отклоняет с обратной связью |
| `shutdown_request` / `shutdown_approved` / `shutdown_rejected` | вежливая остановка участника с причиной |
| `mode_set_request` | смена режима работы участника |
| `permission_request` / `permission_response` | тиммейт просит разрешение на вызов инструмента |
| `sandbox_permission_request` / `…_response` | то же для песочницы |
| `idle_notification` | конец хода: почему встал и что успел |

Сообщение о разрешении несёт имя инструмента, идентификатор вызова, описание и входные данные,
а ответ — либо успех с обновлённым входом, либо отказ с текстом ошибки. Это и есть место, где
агент **не решает сам**: опасное действие уходит наверх, к лиду, и дальше к человеку.

## Idle — норма, а не сбой

После каждого хода тиммейт встаёт и отправляет уведомление лиду: причина (`available`,
`interrupted`, `failed`), завершённая задача и её статус, при неудаче — причина. В промпте лида
это описано отдельным абзацем с требованием терпения: простой после сообщения не означает, что
агент закончил или недоступен.

Два следствия, которые стоит перенести в свои правила:

- сообщение вставшему агенту **будит** его — «занятости» как состояния в протоколе нет;
- в уведомлении о простое видно резюме переписки тиммейта с другим тиммейтом — так лид узнаёт о
  горизонтальных договорённостях, не читая всю переписку.

## Доставка и порядок

Сообщения, отправленные во время чужого хода, копятся и доставляются по его окончании; адресат
считается живым всегда. Поэтому в промпте нет ни опроса, ни ретраев: отправитель просто пишет.
Цена решения — отсутствие гарантии «прочитано сейчас»: статус прочтения ставится на стороне
получателя, когда он до сообщения дошёл.

## Доска задач

Единица передачи работы — не сообщение, а задача на общей доске. Участники создают, читают,
меняют владельца, закрывают; владельца можно передать, но нельзя «захватить чужую» без записи.
Порядок предпочтения — по идентификатору, потому что ранние задачи обычно готовят контекст для
поздних. После завершения задачи агент снова смотрит доску, а не ждёт сообщения.

Практика, которую легко пропустить: в промпте запрещено присылать друг другу JSON-статусы вида
«я встал» или «задача готова» — для состояния есть доска и уведомления, а переписка остаётся
для того, что нельзя выразить статусом.

## Обязанности лида

1. Создать команду (вместе с доской).
2. Создать задачи.
3. Поднять тиммейтов, подобрав тип агента под задачу: read-only агентам не дают правок.
4. Раздать владение задачами.
5. Ждать: простой — норма, реагировать только когда он мешает делу.
6. Погасить команду запросом на остановку, а не обрывом.

## Что берём себе

Для нашей практики (навык `vector-ai-team`, правила делегирования) переносятся семь вещей:

1. Адресация по имени, а не по внутреннему id — читаемо и переживает перезапуск.
2. Задача на общей доске как единица передачи; переписка — только для того, что нельзя выразить
   статусом задачи.
3. У каждой просьбы `request_id`; ответ без него не сопоставить.
4. Простой — штатное состояние; «молчит» не значит «сломался».
5. Разрешения на опасные действия идут наверх, к лиду и человеку, а не решаются исполнителем.
6. Широковещание — дорогая операция с явным обоснованием.
7. Запрет на вложенных тиммейтов: глубина дерева задаётся сверху.
