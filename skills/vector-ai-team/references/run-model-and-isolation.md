# Модель запуска и граница изоляции в Multica — выжимка

Разбор Multica v0.7.2 (`multica-ai/multica`, Go + Next.js + PostgreSQL, Apache-2.0 с дополнительными
условиями) по их документации и исходникам, плюс проверка на живом self-host, поднятом на этой
машине. Всё, что ниже, — пересказ своими словами и результат собственного прогона, а не копия
документации.

Проверено вживую 01.11.2026: compose-стек из образов GHCR (backend, web, postgres 17 с pgvector),
`DO_NOT_TRACK=1`, вход по фиксированному коду (APP_ENV=development), отдельный контейнер-рантайм
(Node 22 + Claude Code 2.1.316 + CLI 0.7.2, пользователь `agent`), одна задача на доске, один
запуск агента. Что не проверялось — в конце.

## Задача и запуск — разные вещи

Единица работы — **задача** (issue). Единица исполнения — **запуск** (run): одна задача может
пережить сколько угодно запусков, каждый пишется отдельной записью, старые не перезаписываются.
Задачу можно передать другому агенту, вернуть прежнему, перезапустить после падения — история
запусков при этом остаётся.

Запуск стартует из пяти источников: назначение исполнителя, упоминание в комментарии, сообщение в
чате, автопилот по расписанию или событию, «пробуждение» задачи по времени/событию/условию.
Контекст у агента в каждом входе свой, но механизм один: создаётся запуск, рантайм его забирает,
рантайм вызывает CLI агента.

Это же разделение объясняет, почему «запуск завершён» ≠ «задача сделана»: завершение запуска
говорит только о том, что конкретное исполнение закончилось нормально, статус задачи ставится
отдельно.

## Жизненный цикл и таймауты

| Состояние | Что значит | Граница |
|---|---|---|
| `deferred` | ждёт назначенного времени | в назначенный момент уходит в очередь |
| `queued` | ждёт, пока рантайм заберёт | не истекает, пока машина на связи; падает, только если молчание машины дольше окна переподключения **и** запуск ждал столько же |
| `dispatched` | рантайм забрал, поднимает CLI | дольше **5 минут** в этом состоянии = падение |
| `waiting_local_directory` | каталог занят другим запуском | своего таймаута нет, ждёт освобождения |
| `running` | CLI работает | потолка по длительности нет; живость — по heartbeat раз в 15 с; машина считается офлайн примерно через 3 минуты молчания, а её запуски падают только после окна переподключения (по умолчанию **3 часа**) |
| `completed` / `failed` / `cancelled` | итог | — |

Смысл цифр: сервер **не убивает длинную работу** и не считает очередь просроченной, если машина
жива. Наоборот, спящей машине дают полное окно, чтобы её разбудили.

## Ретраи

Автоматически повторяются только транзитные сбои, и только у запусков, привязанных к задаче или
чату (режим автопилота «только запуск» не повторяется, чтобы не наложиться на следующее
расписание):

| Причина | Потолок |
|---|---|
| машина ушла в офлайн | 2 попытки (первый + один повтор) |
| запуск отобран после перезапуска демона | 2 |
| таймаут исполнения по решению платформы | 2 |
| Codex замолчал без содержательного вывода | 2 |
| не скачался набор навыков | 2 (процесс агента ещё не стартовал) |
| сетевой сбой внутри инструмента | до 3, последняя через ~5 секунд |

Всё остальное — авторизация, квота, конфигурация, недоступная модель — не повторяется: сначала
чинят причину, потом повторяют руками. Ручной повтор вызывает **того агента, который вёл этот
запуск**, даже если задача уже передана другому, и старается сохранить уже написанные файлы;
`--fresh` начинает с чистого сеанса и каталога.

## Где это исполняется

Демон живёт **на машине**, а не в контейнере сервера. Рантайм — это машина, зарегистрированная в
рабочей области; агент привязан к рантайму. Один демон по умолчанию ведёт до **20** запусков
одновременно, один агент — до **6**; действует меньшее из двух.

Каждый запуск получает свой каталог под общим корнем (по умолчанию `~/multica_workspaces`), и
повторные запуски той же задачи переиспользуют его. Для репозиториев держится один общий
bare-кэш на рабочую область, а из него на каждый запуск делается git worktree — не клон.

Ретенция: каталог задачи удаляется, когда задача в статусе «сделано» или «закрыто» и не менялась
24 часа; через 12 часов после запуска удаляется только регенерируемое (`node_modules`, `.next`,
`.turbo`); кэш репозитория — когда на него 30 дней никто не ссылался. Демон, подключённый к
облачной версии, дополнительно чистит каталоги через 14 дней; self-host так не делает.

## Граница изоляции

Ключевое утверждение их документации, и его стоит цитировать в своих правилах: **граница — это
пользователь ОС, под которым работает демон**. Запуск исполняется с полными правами этого
пользователя: читает и пишет всё, что может он, пользуется его учётными данными, ходит в сеть без
ограничений.

Что Multica действительно изолирует (снижение радиуса, но не защита от попытки выйти):

- свой рабочий каталог на запуск — параллельные запуски не мешают друг другу;
- свой `CODEX_HOME` на запуск для Codex — настройки запуска не пачкают `~/.codex`;
- **токен запуска**: демон выдаёт процессу `MULTICA_TOKEN`, привязанный сервером к паре «агент +
  запуск», поэтому из запуска нельзя действовать ни от имени человека, ни от имени другого агента.

Что границей не является:

- настройки песочницы самого CLI и автоответ на подтверждения. Агенты работают без надзора,
  подтверждения выдаются автоматически; Claude Code запускается с `--permission-mode
  bypassPermissions`, Codex — с `danger-full-access`. Исключение одно: Windows, где при явном
  включении родной песочницы Codex режим `workspace-write` соблюдается;
- раскладка домашнего каталога: запуск наследует настоящий `HOME` и `XDG_*`, именно поэтому внутри
  работают `gh`, `aws`, `kubectl` — и именно поэтому доступно всё, что лежит в этом доме.

Историческая деталь, которая объясняет их выбор: на Linux Codex одно время работал под
`workspace-write` с подменённым `HOME`, но это убрали — хостовые CLI оставались неаутентифицированы
внутри запуска, а от чтения и выноса учётных данных такой режим не защищал всё равно.

Проверить, с чем реально пошёл запуск, можно в логе демона (он пишет уровень песочницы строкой
`codex sandbox` при старте запуска) и в управляемом блоке `config.toml` внутри `CODEX_HOME` запуска,
между маркерами `# BEGIN multica-managed` и `# END multica-managed`.

## Права на агентов

У агента один владелец и настройка доступа: «только я», «вся рабочая область», «конкретные люди».
Доступ определяет, кто может назначить агента на задачу, упомянуть его или писать ему в чат.
Владелец и админ рабочей области видят и правят конфигурацию любого агента, но **не могут обойти
доступ** и запустить чужого агента с настройкой «только я». Менять доступ вправе только владелец
агента. Переменные окружения и MCP-настройки, где лежат секреты, читаются по отдельным, более
строгим правилам.

## Аудит

На задаче видно: кто из агентов работал, чем закончился каждый запуск, транскрипт с вызовами
инструментов и текстом ошибок, потраченные токены, время агента и оценку стоимости по каждому
запуску. Транскрипт досмотренного запуска продолжает стримиться, пока окно открыто. Изменение
исполнителя или статуса задачи **не останавливает** уже идущий запуск — останавливают отдельно, а
удаление задачи отменяет её активные запуски.

## Что мы видели на своём прогоне

Self-host на этой машине, стек в контейнерах, интерфейс и API — только на 127.0.0.1 (backend 8099,
web 3100), телеметрия выключена (`DO_NOT_TRACK=1` в окружении backend; записей об отправке в логах
не было). Рантайм — отдельный контейнер с собственным пользователем `agent`, внутри которого стоит
CLI агента; демон поднят под этим пользователем, а не от root.

Одна задача, один запуск: агент открыл задачу, посчитал, ответил комментарием и перевёл её в
«In Review» сам. Числа в ответе — 128 мм делительный диаметр и 64π ≈ 201,06 мм ход рейки за
полуоборот — совпали с контрольным расчётом. Стоимость показана как оценка, токены — 130,6 тыс. на
задачу, время агента 25 секунд. Никакой ручной сборки отчёта не потребовалось: всё это уже лежит
на задаче.

## Что переносим себе

1. **Задача и запуск — разные сущности.** История запусков не перезаписывается; «запуск прошёл» не
   равно «работа сделана».
2. **Ревью-гейт статусом, а не обещанием.** Агент кладёт результат в «на ревью», в основную ветку
   ничего не уходит само.
3. **Сервер отдельно, исполнитель отдельно.** Доска не держит ключи; ключи остаются на машине, где
   идёт исполнение.
4. **Потолки на параллельность** — на агента и на машину, с очередью вместо отказа.
5. **Граница — пользователь ОС.** Песочница CLI — удобство, а не защита; это надо писать прямо, а не
   подразумевать.
6. **Токен на запуск, а не на человека.** Процесс получает урезанный токен, привязанный к агенту и
   запуску; выйти за его пределы нельзя даже при компрометации.
7. **Ретрай возвращает исходного исполнителя**, а не текущего, и сохраняет уже сделанное.
8. **Ретенция рабочих каталогов по статусу задачи**, а не «когда-нибудь».

## Что не проверено

- Работал только провайдер Claude Code. Codex, Cursor, Kimi, OpenClaw и прочие адаптеры не
  запускались; их особенности (например, песочница Codex на Windows) взяты из документации.
- Отсутствие исходящих запросов телеметрии подтверждено только отсутствием обращений в логах
  backend; сниффером трафик не смотрел.
- Многопользовательский сценарий (несколько людей, разные уровни доступа, «только я» против «вся
  область») не воспроизводился: в живом стенде один пользователь-владелец.
- Helm-развёртывание и облачная версия не проверялись; стек поднимался через compose.
- Нагрузочные пределы (20 запусков на демон, 6 на агента) взяты из документации, а не измерены.
